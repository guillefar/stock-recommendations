## Learnings

The arc: s26 — a loop amplifies bad data. s27 — fixing the data doesn't fix the loop. s28 — a fix keyed on a field inherits that field's gaps. **s29 — the loop was never going to be fixed by making it more accurate, and three sessions of accuracy work is what it took to see that.**

1. **Accuracy and usefulness are different axes, and improving one can destroy the other.** The pattern sets that collapsed decisiveness were the *best* the miner has ever produced — corrected bands, corrected cohorts, corrected asset classes, a mechanical gate. Sessions 26, 27 and 28 each made the loop's inputs more truthful and each time the output got worse, because a true statement about a dead regime is still the wrong instruction for a live one. **When successive quality improvements don't improve the outcome, stop improving quality and question whether the component should exist.**
2. **Three sessions asked the same question and none could answer it, because the independent variable wasn't in the data.** "Is BUY being suppressed?" was unanswerable from a date-indexed action mix, because *which pattern set reached the prompts* lived only in workflow logs and had to be reconstructed by comparing timestamps. The answer took ten minutes once the injected set was a column next to the decisive count. **A metric table without its independent variable is not evidence, however many rows it has.**
3. **Turning a suspect component off is a measurement, and usually the cheapest one available.** HANDOFF_28 flagged this ("pausing a feedback loop is a legitimate, cheap experiment") and it paid immediately — one run, one number, 2 → 9. Three sessions had instead tried to *reason* about whether the loop caused the suppression. **A/B is available on anything you can switch off; reach for it before the third round of analysis.**
4. **The control you need can be a side effect of a deploy — notice it.** 08-14's no-injection run wasn't designed; it happened because the s28 gate failed closed on a stale set. It would have been easy to read the recovery as "the merge helped" and move on. **When something changes between two measurements, enumerate everything that changed, not just the thing you were working on.**
5. **A fix aimed at a symptom you've already characterised can still miss.** The |excess| ranking was pinned by two consecutive handoffs as *the* answer to session 27's finding. It was checked against the live data before being built, and it ranks the harmful pattern second — identical to what it replaces. **Before implementing a slice inherited from a previous session, re-derive that it still solves the problem; the corpus it was designed against has moved.**
6. **"Conservative" defaults keep being the trap.** Session 28's learning was that falling back to unscaled bands wasn't conservative for a low-volatility fund. Session 29's switch defaults to *off* for the same reason inverted: with a component whose net effect is unproven, the safe default is not-running, and "leave it on until we know" is a strong opinion disguised as caution. **Name what the default is safe relative to.**
7. **A diagnostic that requires a specific human at a specific computer on a specific day is not a diagnostic.** `check_run.py` was written in session 27 to make post-run verification a one-command habit; it then went unrun for eleven days because the one machine with the `.env` was unattended. Twenty lines moved it into the pipeline that produces the data. **Automate the reading, not just the writing.**
8. **The model reproduces a known error for the third consecutive session.** id=7 carries `WATCH … colapso a 0% acierto` at CONFIRMED 0.76 with its own `excess_return_pp` field reading **+10.2**. Sessions 27, 28 and 29 all recorded this verbatim. **It is a property of the miner. Stop spending prompt words on it.**
9. **Elapsed time between sessions is a feature.** Sessions 27 and 28 both ran the same day as their predecessor and neither could test anything. Eleven days of unattended production produced the single most informative dataset the project has had. **When the next slice is calendar-gated, the right move may be to wait rather than to find something else to build.**

## Invariants (don't break)

All of HANDOFF_28's invariants stand — in particular **excess is direction-blind**, **the market cohort is `(rec_date, ETF vs non-ETF)`**, **`src.quote_types` only ever fills gaps** and **any change to it needs a `--regrade` with sign-off**. New this session:

- **Pattern injection is off unless `PATTERN_INJECTION_ENABLED` is truthy.** Test-pinned, including that an unset environment means off. Do not invert the default "temporarily".
- **Re-enabling requires evidence about *outcomes*, not accuracy.** The sets that caused the collapse were the most accurate ever mined. A better miner is not an argument for switching it back on.
- **Mining keeps running with injection off.** `prediction_patterns` must keep accumulating — it is the analysis corpus, and the rows written during the off period are what a future re-enable case will be argued from.
- **The switch is checked in `select_patterns_for_prompt`, not at the call sites.** One choke point, same reasoning as s28's "apply quote_type overrides at the DB read sites".
- **`check_run.py` never writes**, and its workflow step is `continue-on-error` — a health check must never turn a green run red.
- **Report each run against what it injected.** If a new pattern set starts reaching prompts, add it to `check_run.py`'s `INJECTED` map, or the table silently becomes uninterpretable again.
- **The `_patterns_block` regime caveat stays** while the loop's net effect is unproven — a third condition that supersedes HANDOFF_26's and HANDOFF_27's, both of which are now satisfied.
